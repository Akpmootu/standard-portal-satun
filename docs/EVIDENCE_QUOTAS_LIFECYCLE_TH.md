# ขั้นที่ 2 — โควตาและวงจรไฟล์หลักฐาน

## ขีดจำกัดของแอป

| ขอบเขต | จำนวน | พื้นที่ |
| --- | ---: | ---: |
| ต่อบัญชี | 100 ไฟล์ | 50 MB |
| ต่อหน่วยบริการ | 500 ไฟล์ | 200 MB |
| ทั้งระบบ | 4,000 ไฟล์ | 1,024 MB |
| ต่อบัญชีต่อวัน เวลาไทย | 10 ไฟล์ | 20 MB |
| ไฟล์ที่ยังไม่แนบต่อบัญชี | 20 ไฟล์ | รวมในเพดานข้างต้น |

รูปใหม่ยังจำกัด JPG/PNG/WebP ไม่เกิน 2 MB ต่อไฟล์ PDF ให้ใช้ลิงก์ Google Drive ตามเดิม ขีดจำกัดเหล่านี้เป็นนโยบายของแอป ไม่ใช่ตัวเลขพื้นที่ว่างจริงของบัญชี Google Drive และไม่รวมไฟล์นอกระบบ

นับทั้งไฟล์ที่กำลังอัปโหลด ไฟล์ที่เสร็จแล้ว ไฟล์ที่พัก และไฟล์ที่ย้ายไปถังขยะแล้ว ตัดออกจากโควตาสะสมเฉพาะเมื่อแอดมินตรวจด้วยบัญชีเจ้าของว่าไม่พบไฟล์แล้ว ไฟล์ที่ปลดโควตาในวันเดียวกับวันที่อัปโหลดยังถูกนับในโควตารายวัน จึงไม่สามารถวนสร้าง–ย้าย–คืนพื้นที่เพื่อหลบเพดานรายวันได้

Node ตรวจเบื้องต้นก่อนขอ Drive ID ส่วน Apps Script ตรวจโควตาอีกครั้งภายใน ScriptLock และบันทึก files/audit/receipt ใน batch เดียว คำขอพร้อมกันจึงไม่ใช้ยอดเก่าจนทะลุเพดาน โครงสร้างชีตเดิมไม่เปลี่ยน

## หน้าจัดการไฟล์

เปิด `/files` จากเมนู **ไฟล์หลักฐาน / พื้นที่** ผู้ใช้หน่วยบริการเห็นเฉพาะไฟล์ของตนในหน่วยบริการปัจจุบัน แอดมินตรวจไฟล์ทั้งหมดได้ ผู้ตรวจ MOU ไม่มีสิทธิ์จัดการไฟล์

- แสดงพื้นที่สะสม รายวัน และจำนวนไฟล์ที่ยังไม่แนบ พร้อมสถานะของแต่ละไฟล์
- ไฟล์ที่มีการอ้างอิงใน mou_progress, ctam_progress หรือ rg12_progress ไม่มีปุ่มพักไฟล์ และ API/Writer ปฏิเสธซ้ำด้วย ไม่ตรวจเพียงว่าชื่อไฟล์หรือ record_id ตรงกัน
- ไฟล์ไม่แนบเกิน 24 ชั่วโมงแสดงให้ตรวจสอบ ไม่มีการย้ายหรือลบอัตโนมัติ
- ปุ่มพักไฟล์มี dialog ในหน้าเว็บ กดยกเลิกหรือ Escape แล้วไม่ส่งคำขอ
- สถานะ `uploading/complete → retiring → trashed → released` เก็บขนาดและประวัติเดิมไว้ ไม่ลบแถวข้อมูล

## ขั้นตอนย้ายไฟล์ที่ไม่ใช้แล้ว

1. ผู้สร้างไฟล์หรือแอดมินเลือกพักไฟล์และยืนยัน ระบบตรวจสิทธิ์ สถานะ เวอร์ชัน และรายการอ้างอิงภายใต้ล็อกก่อนเปลี่ยนเป็น `retiring`
2. รออย่างน้อย 120 วินาทีให้คำขออัปโหลดที่เริ่มไปก่อนหน้าจบ โทเคนอัปโหลดเก่าและการแนบใหม่ใช้ไฟล์ที่พักแล้วไม่ได้
3. กดดำเนินการย้ายต่อ คำขอเดิมส่งซ้ำได้โดยไม่สร้างธุรกรรมซ้ำ หากโหลดหน้าใหม่จะใช้เวอร์ชันปัจจุบันและตรวจเวลาจาก audit
4. Node ตรวจว่า Drive object เป็นไฟล์ของแอป อยู่ในโฟลเดอร์ที่กำหนด และมีเจ้าของ/สิทธิ์ส่วนตัวตรงบัญชีหน่วยงาน ก่อน PATCH `trashed:true` เท่านั้น ไม่มี DELETE ถาวร
5. ย้ายสำเร็จแล้วสถานะเป็น `trashed` แต่ยังนับพื้นที่ หาก Drive หรือการบันทึกตอบไม่ชัดเจนจะคงสถานะพักและคงโควตาไว้จนตรวจซ้ำ ไม่คืนโควตาโดยเดาว่าสำเร็จ
6. เมื่อไฟล์ไม่อยู่แล้ว แอดมินจึงกดตรวจยืนยันการคืนพื้นที่ ระบบตรวจ email ของบัญชี metadata-read ว่าตรงเจ้าของก่อนรับ HTTP 404 จาก Drive เป็นหลักฐาน จากนั้น Writer ตรวจสิทธิ์ เวอร์ชัน และรายการอ้างอิงอีกครั้ง จึงเปลี่ยนเป็น `released`

การตรวจเจอไฟล์เดิมอยู่ ไม่ว่าพักอยู่หรืออยู่ในถังขยะ จะไม่คืนโควตา การคืนพื้นที่จริงใน Google Drive อาจต้องรอกระบวนการของ Google หรือผู้ดูแลจัดการภายใต้นโยบายของหน่วยงาน แอปนี้ไม่ลบถาวรให้

## หลักฐานทดสอบและเผยแพร่

- ชุดทดสอบรวม 208 รายการผ่าน รวมโควตา completed/unattached, เพดานไบต์, เพดานรายวัน, การนับถังขยะ, การปฏิเสธไฟล์อ้างอิงข้ามโมดูล, โทเคนเก่าหลังพัก, การตรวจเจ้าของ Drive และ idempotent retry
- ทดสอบ Writer ที่ build ใน VM รวมการบังคับโควตาภายใต้ล็อกและการไม่ commit เมื่อมีรายการอ้างอิง
- Apps Script deployment เดิมอัปเดตเป็นเวอร์ชัน 8 วันที่ 26 ตุลาคม 2569 โดยไม่เปลี่ยน URL ผู้เข้าถึง หรือ OAuth scopes; GET ที่ deployment จริงยืนยัน `evidencePolicy:2`
- เบราว์เซอร์ Codex ตรวจข้อมูลสมมติ: dialog ยกเลิกได้, ย้ายไฟล์ไม่แนบได้, ไฟล์อ้างอิงไม่มีปุ่มจัดการ และไฟล์ยังอยู่ไม่ถูกคืนโควตา; ไม่ทำลายไฟล์จริงเพื่อทดสอบ
- ตรวจหน้าในความกว้างจริง 320 px รวมขนาดแท็บเล็ต/เดสก์ท็อป ไม่พบเนื้อหาล้นแนวนอน

## ย้อนกลับและการดูแล

ไม่ย้อนกลับ Writer เป็นเวอร์ชันก่อนมีโควตาโดยพลการ เพราะจะทำให้การกันคำขอพร้อมกันหายไป หากเว็บมีปัญหาให้ปิดการอัปโหลดผ่าน gate เดิมชั่วคราวและคงการอ่าน/ลิงก์ PDF ไว้ ข้อมูลสถานะใหม่ต้องเก็บไว้เพื่อกระทบยอดก่อนเปิดรับอัปโหลดอีกครั้ง

การย้ายไฟล์ที่มนุษย์แก้ข้อมูลชีต/Drive โดยตรงอยู่นอก ScriptLock ควรหยุดแก้ตรงขณะจัดการไฟล์ผ่านแอป การสำรองและประวัติการประเมินเป็นคนละขั้นกับการจัดการไฟล์ไม่แนบ ต้องปฏิบัติตามนโยบายเก็บรักษาของหน่วยงาน
