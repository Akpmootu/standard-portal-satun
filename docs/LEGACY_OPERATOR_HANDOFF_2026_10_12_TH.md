# ชุดตรวจและพักระบบเดิมสำหรับผู้ดูแลเซิร์ฟเวอร์

สถานะ 12 ตุลาคม 2569: เจ้าของพร้อมประสานผู้ดูแล root แต่ยืนยันให้คงรอคำตอบเรื่อง Vercel จึงยังไม่สั่งหยุดเขียนหรือปิดเว็บเดิม เอกสารนี้เป็นขั้นตอนที่เตรียมให้ตรวจ ไม่ใช่บันทึกว่าติดตั้งแล้ว

## งานที่ผู้ดูแลทำได้ก่อนวันสลับ

1. รับไฟล์ `ops/legacy-operator-preflight.php` และ `ops/legacy-maintenance-location.conf` จากชุดโครงการที่ตรวจแล้ว เก็บในพื้นที่ส่วนตัวของ root สคริปต์ PHP อ่านอย่างเดียว ไม่เชื่อมฐานข้อมูล ไม่ปิดงานและไม่แก้ config ผ่านการตรวจ syntax ด้วย PHP บนเซิร์ฟเวอร์จริงแล้ว
2. รัน preflight ด้วยบัญชี root ที่ได้รับอนุญาต เก็บ JSON โดยใช้สิทธิ์ไฟล์ 600 หรือ umask 077 ตรวจ `runningAsRoot: true` รายงานเฉพาะตำแหน่งงาน/เลขบรรทัด/แฮช/ชื่อสคริปต์ ไม่แสดงคำสั่งเต็มหรือ token
3. ตรวจ crontab ของ root และผู้ใช้ทุกบัญชีที่มีงาน รวม `/etc/crontab`, `/etc/cron.d`, systemd timers/services และ drop-ins, container/workers รวมตัวเรียกจากภายนอกที่อาจยิง HTTP เข้ามา ยืนยันว่ามีหรือไม่มีการเรียก `cron_daily_summary.php`, `cron_deadline_reminder.php`, `cron_weekly_summary.php` หรือเส้นทาง `hait-RG12` รายงานอัตโนมัติไม่ครอบคลุมการตั้งเวลานอกเครื่อง ต้องตรวจส่วนนี้ด้วยคน
4. ระบุรายการที่จะพักพร้อมวิธีย้อนกลับ แยกเฉพาะระบบประเมินออกจากเว็บประชุม `/digital_stn/meeting_daily/` และบริการร่วมเครื่อง ไม่หยุด cron, Nginx หรือ PHP-FPM ทั้งระบบ
5. ตรวจ `readlink -f /etc/nginx/sites-enabled/hait-status.conf` และ include/alias/เส้นทางเข้าทางเลือกของแอป เก็บ config และรายการงานเดิมในพื้นที่ส่วนตัวของ root พร้อมแฮชและเวลา ทดสอบ `nginx -t` กับ config เดิมไว้ก่อน ไม่ส่งไฟล์ config หรือ crontab ที่มีความลับมาในแชท

## ลำดับในช่วงหยุดบันทึกที่อนุมัติแล้ว

1. สำรองเว็บใหม่และคลังต้นฉบับก่อนพัก รวม config/งานเดิมที่ root เก็บไว้ ระบุเวลาตัดข้อมูล
2. พักเฉพาะงาน CLI/systemd/ตัวตั้งเวลาภายนอกที่ตรวจพบว่าเขียนหรือส่งแจ้งเตือนจากระบบเก่า เก็บรายการที่พักและค่าเดิมทุกงาน
3. วาง maintenance snippet ภายใน `server {}` เดิมที่ตรวจแล้ว ให้ครอบคลุม exact `/digital_stn/hait-RG12` และ prefix `/digital_stn/hait-RG12/` ตรวจไม่ซ้ำ location เดิมและไม่มี alias/ทางเข้าหลบไป PHP ระบบเก่า ไม่แทน vhost ทั้งชุด
4. รัน `nginx -t` หลังแก้ ถ้าไม่ผ่านให้คืน config และหยุดขั้นนี้ ห้าม reload เมื่อ syntax ไม่ผ่าน เมื่อผ่านจึงใช้ `systemctl reload nginx` ไม่ stop/restart ทั้งเครื่อง
5. ตรวจ GET/POST/API/cron URL และ session เก่าของแอปได้รับ 503 และไม่เขียนข้อมูลจริง หน้า maintenance แสดงลิงก์ https://standard-portal-satun.vercel.app/ ไม่มีการส่ง payload POST ไปเว็บใหม่ ตรวจเว็บประชุมเดิมยังทำงาน
6. ส่งออกฐานข้อมูลเก่าแบบอ่านอย่างเดียวอีกครั้งหลังพัก เทียบครบ 20 ตารางทั้งค่าธุรกิจ ชนิดข้อมูล NULL และแถวซ้ำ พร้อมตรวจไฟล์ซ้ำ ถ้าพบส่วนต่างให้หยุดการประกาศสลับและกระทบยอดอย่างเจาะจง ห้ามนำ snapshot เก่าเขียนทับธุรกรรมที่เกิดในเว็บใหม่
7. สำรองหลังพักและหลังเทียบ ตรวจบทบาท ประวัติ รายงาน ไฟล์ และการลงชื่อเข้าใช้ใหม่ เจ้าของลงนามตรวจรับแล้วจึงประกาศเว็บใหม่เป็นแหล่งข้อมูลหลักเพียงแห่งเดียว

คำสั่งตรวจบนเครื่องเจ้าของจากโฟลเดอร์โครงการ: `node scripts/check-source-archive-delta.js administrator <path-to-existing-SSH-key>` และ `node scripts/check-source-asset-delta.js administrator <path-to-existing-SSH-key>` ใช้การเชื่อมต่อเดิม ตรวจ host key และไม่เขียนต้นทาง ต้องรันใหม่หลัง freeze ผลก่อน freeze ใช้แทนไม่ได้

## การย้อนกลับ

การคืน Nginx config เพียงอย่างเดียวไม่คืนข้อมูลใน Google Sheets ก่อนเปิดให้เขียนระบบเดิมอีกครั้ง ต้องพักการเขียนเว็บใหม่ที่ gate ของเว็บและ Apps Script writer สำรองสถานะใหม่และเก็บธุรกรรมหลังสลับ กระทบยอดแล้วกำหนดแหล่งข้อมูลหลัก ห้ามเปิดสองระบบเขียนพร้อมกัน

ดู `docs/BACKUP_RESTORE_TH.md` สำหรับการกู้ข้อมูลแยกและตรวจอ่านกลับ เมื่อตัดสินใจย้อนกลับจึงให้ root คืนเฉพาะ config/งานที่พักไว้ ตรวจ `nginx -t` และ reload พร้อมตรวจเว็บร่วมเครื่อง ห้ามลบฐานข้อมูล ประวัติ หรือไฟล์สำรอง

## ผลที่ต้องส่งกลับเพื่อปิดงาน

ส่งเฉพาะผล preflight ที่ไม่มีความลับ ชื่อผู้ดูแล เวลา งานที่พัก ผล syntax/reload ผลทดสอบ GET/POST/เว็บประชุม และแฮชสำรอง รายงานไม่ต้องมีรหัสผ่าน กุญแจ token crontab เต็ม หรือ config เต็ม ยังไม่มีการติดตั้ง snippet หรือพักงานใดโดย Codex ในรอบนี้
