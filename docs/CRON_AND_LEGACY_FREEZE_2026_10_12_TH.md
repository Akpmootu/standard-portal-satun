# ตรวจการแจ้งเตือนและเตรียมพักระบบเดิม — 12 ตุลาคม 2569

## แก้ผลตรวจของงานตามเวลา

ก่อนแก้ `/api/integrations/cron` ตอบ HTTP 200 และ `ok:true` แม้ผลส่ง Telegram รายวัน/รายสัปดาห์มี error ทำให้ดูเหมือนงานสำเร็จ

หลังแก้ งานที่อ่านสรุปหรือส่งข้อความไม่สำเร็จตอบ HTTP 503 และ `ok:false` โดยไม่ส่งซ้ำอัตโนมัติ งานที่มีการจองช่วงเวลาส่งไว้แล้วจะถือว่าข้ามได้ต่อเมื่อ audit มี reservation เดียวและ settlement เดียวที่ยืนยัน `sent` เท่านั้น ถ้าผลเดิมไม่แน่นอนหรือไม่มี settlement ให้รายงาน `SCHEDULED_DELIVERY_UNCONFIRMED` แทนการรายงานสำเร็จ ไม่สร้างการส่งซ้ำเพื่อแก้ความไม่แน่นอน

เพิ่ม runtime log `portal_cron` ระบุเริ่ม/จบ/ล้มเหลว ช่วงวันที่ เวลาเริ่ม/จบ และจำนวนส่ง/ข้าม/ผิดพลาด ไม่บันทึก token, chat ID, อีเมล, รายละเอียดผล, ข้อความ Telegram, รหัสหน่วยบริการ หรือ message ID ต้องใช้ log นี้ร่วมกับ scheduler invocation จริงและ audit ของชีต ไม่ถือว่าการเรียก endpoint ด้วยมือเป็นหลักฐานของตัวตั้งเวลา

การทดสอบใช้เซิร์ฟเวอร์ HTTP และ writer/sender จำลอง ไม่มีการส่ง Telegram จริงเพิ่มในรอบนี้ ครอบคลุม bearer ผิดไม่ส่ง/ไม่ log, ส่งสำเร็จ, ไม่แน่นอนแล้วไม่ retry, ข้ามรายการที่ยืนยันส่งแล้ว, ไม่ถือว่ารายการเดิม uncertain ส่งแล้ว, อ่านข้อมูลล้มเหลว และไม่เผยรายละเอียด provider ใน log/response

ตารางยังเป็น 09:00 น. ไทย รายวันและวันจันทร์รายสัปดาห์ ไม่มีการเปลี่ยนตาราง รอบจริงถัดไปหลังการแก้คือวันที่ 13 ตุลาคม 2569 และรายสัปดาห์วันที่ 19 ตุลาคม 2569 เวลา 09:00 น. ตามข้อจำกัดช่วงเวลาของโฮสต์ ยังไม่ถือว่าผ่านจนเห็นการเรียกจริงที่ตรงกัน ไม่ได้ตั้งระบบติดตามอัตโนมัติเพิ่มในแชทนี้

## โครงสร้างเว็บเดิมที่ตรวจจริง

ตรวจ 15:05–15:06 น. ไทยแบบอ่านอย่างเดียว พบ Nginx, PHP-FPM 8.3 และ cron ทำงานอยู่ Vhost `/etc/nginx/sites-enabled/hait-status.conf` ใช้ root `/var/www/html` และมีเส้นทางเว็บประชุม `/digital_stn/meeting_daily/` ร่วมด้วย จึงห้ามปิด Nginx ทั้งเครื่องหรือแทน vhost ทั้งชุดเพื่อปิดเฉพาะระบบประเมิน

บัญชี SSH administrator ไม่มี user crontab การอ่าน root crontab แบบ non-interactive ด้วยสิทธิ์ที่มีอยู่ไม่สำเร็จ ไม่มีการขอรหัสผ่าน/แก้ sudoers/สลับบัญชีเพื่อข้ามข้อจำกัด ต้องให้ผู้ดูแล server ตรวจ root/บัญชีอื่น, systemd timers และ scheduler ภายนอกก่อนยืนยันว่า Telegram ระบบเก่าหยุดแล้ว

เตรียม `ops/legacy-maintenance-location.conf` เป็น snippet สำหรับใส่ภายใน server block เดิมหลังผ่านเกณฑ์สลับระบบ ครอบคลุม URL `/digital_stn/hait-RG12` และ `^~ /digital_stn/hait-RG12/` เพื่อให้ Nginx ตอบ 503 แทนการเรียก PHP/API/cron ผ่านเว็บ และแสดงลิงก์ระบบใหม่ ไม่ redirect payload จาก POST ไม่เปลี่ยนเส้นทางเว็บประชุมหรือแอปอื่น

**ยังไม่ได้ติดตั้ง snippet, ยังไม่ได้ตรวจ `nginx -t` บนชุด config หลังติดตั้ง, ไม่ reload Nginx และไม่พัก cron/แก้ไฟล์หรือ DB ต้นทาง** ไฟล์ที่เตรียมยังไม่ถือว่าผ่านการทดสอบบน server จริง ต้องสำรอง config, ตรวจ alias/include/เส้นทางทางเลือก, syntax test ก่อน reload, ตรวจ GET/POST และ session เดิมถูกพักจริง รวมทั้งตรวจเว็บประชุมเดิมยังทำงาน ก่อนส่งออกรอบ freeze

## MOU/HAIT ที่ตรวจจากเว็บจริง

โรงพยาบาลสตูล 10746 ปี MOU 2569 ไม่มีแถวผลในชีต และปีเก่าล็อกตามกติกาปีปัจจุบัน 2570 จึงไม่เปิดล็อกหรือเปลี่ยนปีเพื่อให้ผลทดสอบผ่าน ไม่มีการบันทึก/อนุมัติ MOU หรือ HAIT ในรอบนี้ HAIT ของ 10746 ยังไม่มีผลบันทึก 44 ข้อ

แก้ข้อความเมื่อ MOU ไม่มีผลบันทึก จากการคาดเดาว่าอาจยังนำเข้าไม่ครบ เป็นการแจ้งให้ตรวจหน่วยบริการ/ปีและติดต่อผู้ดูแลเพื่อดูย้อนหลัง ข้อความไม่ใช้แถวว่างเป็นหลักฐานว่าข้อมูลย้ายขาด ไม่เปลี่ยนข้อมูลประเมิน

ได้รับรายการ MOU 09611 / 2570 / ข้อ 1.1 มี/ผ่านเกณฑ์ รายละเอียด “ทดสอบ” หลักฐาน https://satun.moph.go.th/wordpress/?page_id=271 และ HAIT 10746 / หมวด 1 / มีแผนแม่บท IT เป็นลายลักษณ์อักษร มี/ผ่านเกณฑ์ รายละเอียด “ทดสอบ” แล้ว HAIT ยังขาดผู้รับผิดชอบและลิงก์หลักฐานตามกติกาบังคับ จึงขอข้อมูลเพิ่ม ไม่ใช้หลักฐาน MOU หรือ Backup ของ CTAM แทนโดยอัตโนมัติ การทดสอบการส่งใหม่ของหน่วยบริการต้องได้รับการยืนยันปรับสิทธิ์ชั่วคราวสำหรับรายการใหม่ก่อน

## ขั้นต่อไป

เผยแพร่การแก้ผลตรวจ cron และข้อความ MOU หลังชุดตรวจผ่าน ตรวจวงจร MOU/HAIT เมื่อได้รับข้อมูลจริง ตรวจรอบ cron จริงตามเวลา และให้ผู้ดูแล server ตรวจ root/งานเดิมที่ยังเข้าถึงไม่ได้ ระหว่างรอยืนยันเงื่อนไข Vercel และผู้เก็บกุญแจสำรอง จากนั้นจึงกำหนด freeze/กระทบยอด/ตรวจรับและปิดการใช้งานระบบเดิม
